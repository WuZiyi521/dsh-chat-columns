# 无缝模式（B）的模型说明

这份文档只解释一件事：**B 到底把内容怎么摆**，以及它为什么长这样。
如果你看了实际效果觉得"不对"，先对照这里确认是「实现没达到模型」还是「模型本身不是你要的」。

---

## 1. 定义（来自 3.0 任务书）

```
H = 阅读视口高度（标题栏底部 → 输入框顶部）
s = 主滚动容器的 scrollTop（唯一的逻辑滚动量）
第 c 列显示逻辑内容区间 [s + cH, s + (c+1)H)
```

所以 N=2 时，屏幕上同时呈现的是**两个错开一屏的连续窗口**：

```
左列:  ─── s ────────── s+H
右列:  ─── s+H ──────── s+2H
```

左列底部（`s+H`）和右列顶部（`s+H`）是**同一处内容**，所以接缝两侧内容连续。
`s` 增大时，两列内容一起上移，接缝相对内容连续移动（不是翻页）。

## 2. 为什么「一条消息绝不跨列」

如果按上面的公式直接摆，`y[i]` 是连续累加的，那么跨过 `s+H` 的消息会被列缝切断：
它落在左列的部分可见，落在右列的部分**永远不会出现**（那不是滚动能补回来的，是被裁掉了）。

所以实现里加了一条硬约束：**消息按整列高度 H 打包**（`src/math.js` 的 `pack`）：

- 从第 0 列开始往下排，一条消息放得下就放，放不下就整条挪到下一列顶部；
- 于是每条消息的逻辑起点 `y[i]` 一定是某个 `kH + 列内偏移`，不会跨过列底；
- 代价：某一列底部可能有留白（最多 < 一条消息的高度）。

这就是"列底留白"的来源。它是「不切断消息」的必然代价，不是 bug。
另一条路是允许切断（消息被劈成两半、下半截永远看不到），不可接受。

## 3. 超高消息

单条高度 > H 的消息（典型：几百行的代码块）如果按原高度摆，一定会和相邻消息重叠。
处理方式：**独占一个列段，列内只显示一屏，消息自己内部滚动**（`overflow-y:auto` + `max-height:H`）。

- 不会重叠；
- 内容仍然能读到（在消息内部滚）；
- 代价：这类消息里多一层滚动条。

## 4. 它是 / 不是 什么

| 是 | 不是 |
|---|---|
| 列高 = 阅读视口高度 | 列高 = 内容总高 ÷ 列数（那是报纸 A） |
| 一条消息不跨列 | 消息被列缝劈开 |
| 滚动时接缝相对内容连续移动 | 翻页（点一下换一屏） |
| 原生节点、原生交互、原生滚动容器 | 另建一套只读镜像 |
| 逻辑占位层提供真实滚动条 | 接管滚轮 / 横向滚动 / 第二个滚动容器 |

## 5. 另外两种「一屏一列」的做法（没采用，留档）

1. **按行翻页（spread）**：把页按 N 个一组排成一行，第 r 行显示第 `rN .. rN+N-1` 页。
   滚动一屏 = 换一行。接缝固定相对内容，读起来最像"报纸摊开"，但滚动时接缝不动——
   2.0 时期用户正是把这种效果否掉，认为"还是报纸"。
2. **逐列独立滚动**：每列自己滚自己的。实现最简单，但那是复制模式 C 的行为，不是无缝。

## 6. 判断「实现没达到模型」还是「模型不对」

在控制台跑：

```js
__dshc.diagnose().seamless
```

判读：

| 字段 | 期望 | 不符合说明什么 |
|---|---|---|
| `active` | `true` | 没进入无缝（宽度不够 <2 列 / 初始化失败，看 `.state.prefNote`） |
| `H` | = 阅读视口高度 | 量错了视口（输入框高度没扣掉） |
| `columnWidth` | ≈ (可用宽 - (列数-1)×40) / 列数 | 宽度算错 |
| `pages` | = ceil(内容总高 / H) | 打包没生效 |
| `total` | = `pages × H` | 占位层高度算错 |
| `maxScroll` | = `total - H` | 占位层和滚动容器不一致 |
| `tall` | >0 表示有超高消息被隔离 | —— |

如果 `active:true` 但视觉上内容不动：说明粘滞层没生效（祖先有 `overflow` 裁剪），
这时实现会自动退化成"JS 钉住"（每帧下移 `s`）；若仍然不动，把 `getComputedStyle(列).position` 和祖先链的 `overflow-y` 发我。
