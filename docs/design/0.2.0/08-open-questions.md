# 08 · 需要拍板的问题

> 每一条都写：**为什么必须现在定**、**我的建议**、**不定会怎样**。
> 建议不等于结论——你改一个字，我照新的做。

## Q1 · 无缝模式的「接缝」到底指什么？（**已定：R2**）

> **决定（2026-11-09，维护方）**：采用读法 A —— 流切点钉在 `y = H`，内容穿过接缝。
> 即 **R2（滑动窗口 + 每帧重分片）**。R1 保留为 R2 实测未过门槛时的退路；R3 不启用。
> P1 只攻 R2，不再并行。P1 的滚动写入口径见 **Q5：零写入**。

**问题**：需求写的是「列与列之间的接缝固定在视口底部附近，滚动时连续移动」。这句话有两种读法：

- **读法 A（流切点）**：第 `c` 列显示流区间 `[s+cH, s+(c+1)H)`，切点钉在列底边 `y=H`；
  滚动时是**内容穿过固定的接缝**。→ 对应 R2（滑动窗口）。
- **读法 B（竖缝横移）**：列是固定高度的切片，列与列之间那条竖直缝隙随滚动在视口里**横向移动**。
  → 对应 R1（固定切点 + 横向平移）。

**为什么必须定**：两条读法的实现完全不同（R2 每帧重排、R1 零重排），P1 只能先攻一条。

**我的建议**：读法 A（R2）。理由是「滚动时**连续移动**」说的是阅读位置连续移动，
而读法 B 的接缝横移会让同一行内容在屏幕上的纵向位置不变、横向跳列，不符合「读长文」的直觉。

**不定会怎样**：P1 同时做两条 = 两周变四周，且两条都可能做到一半发现对方才是对的。

## Q2 · 复制模式允不允许用宿主内部服务（`ctx.get`）？

**问题**：`[已证实]` 插件能通过 `ctx.get("sessions")` / `ctx.get("uiConversation")` 读到
`hasMore/loadingOlder/openState` 和节点模型 `{order, nodes}`。但那是对内服务，不在插件契约里，
跨版本可能消失；而且 `ctx.sessions` 这种属性访问会直接抛错（只能 `ctx.get`）。

**为什么必须定**：`[已证实]` DOM 里**没有完整内容**（折叠 JSON 不渲染 payload、展开截断 2 万字符、
`hidden` 行被摘掉）。只用 DOM，C 模式永远是「可能缺内容」。

**已定（2026-11-09）**：允许使用，但**分两层**——DOM 是契约（必须能独立跑通），服务是加速
（启动探测一次，失败永久降级，不重试）。UI 必须显示当前是「完整」还是「降级快照」。

### 两个词必须分清（评审要求）

| | **完整会话数据**（`ServiceSource`） | **DOM 快照**（`DomSource`） |
|---|---|---|
| 来源 | `ctx.get("sessions")` / `ctx.get("uiConversation")` 的节点模型 | 扫 `[data-chat-flow]` 的可见行 |
| 覆盖 | 全部行；折叠 JSON 的 payload 也在 | 只覆盖**渲染出来**的行 |
| 已知缺失 | 无（受宿主内部模型完整度限制） | 折叠 JSON 不渲染 payload；展开截断 **20000 字符**；`hidden` / `hidden="until-found"` 行被摘掉 |
| 标记 | `complete = "full"` | `complete = "partial"` |
| 可承诺给用户的话 | 「完整」 | **只能说「可见内容」** |

### 服务不可用时，复制模式的功能边界（硬规定）

**仍然可用（不降级为不可用）：** 只读分栏、各栏独立滚动、栏头只读标签、共享历史源
（经宿主「加载更早」按钮触发，仍是一次单飞）、代码块复制。

**必须关闭（因为会产出「看起来完整、实际残缺」的东西）：**

1. 「导出/复制全文」一类功能——导出的会是残缺内容；
2. 跨栏「精确定位到第 N 轮」——行序可能缺行，定位会错；
3. 任何声称「全文检索」的能力。

**必须显示：** 栏头常驻「降级快照 · 可能缺内容」标记；进入模式时一次性横幅说明缺什么。

**不受影响：** 报纸（A）与无缝（B）只依赖可见内容和几何，不依赖完整性。

**不定会怎样**：用户拿着残缺副本当全文对照，比没有这个功能更坏。

## Q3 · 「完整内容」是否等于「进入 C 就拉完整个历史」？

**问题**：需求写「每栏显示同一会话的完整内容」，同时又给 C 设了 `autoLoad = true`。

**我的建议**：**不切段 + 按需自动加载**（不是一进模式就拉全量）。理由：全量拉取在 200+ 轮会话上
是几十次分页，与「共享一个历史源、不许重复请求」的约束叠加会变成很长的一次阻塞。

**不定会怎样**：用户以为「完整」= 立刻全在，实际要滚才加载，体验预期落空。

---

## Q4 · 历史加载的 `error` 态允许用「超时/无进展」近似吗？

**问题**：`[已证实]` 宿主把 paging 失败吞掉了（`session-controller:2492-2513`，只 `console.error`）。
DOM 上「失败」「超时」「真的没有更多」三者长得一样。

**我的建议**：接受近似。规则：一批超过 8s 无变化 → `error`；连续 2 批无进展 → 停止并提示
「无法加载更早」；不自动重试超过 3 次。

**不定会怎样**：要么永远等（死循环），要么把「没有更多」误报成错误。

## Q5 · 无缝模式若必须写 `scrollTop`，允不允许开例外？

**问题**：`[已证实]` 批次在途时任何手势都会让宿主放弃锚点补偿；而「滚到顶触发加载」用的正是手势。
三条处置：(a) 等手势静默再加载；(b) 插件补一次 `scrollTop`；(c) 接受整屏位移。

**已定（2026-11-09）**：

1. **P1 的验收口径是「零 `scrollTop` 写入」**，不带任何附条件通过。探针里装写入计数，
   非零即 P1 不通过（见 04 §5 的 T5/T9）。
2. P1 只做 (a)：**等手势静默**（`scrollend` + 停留阈值）再触发加载。
3. **任何例外都走重新审批**，不是 P1 的选项：需要单独出证据（写入次数、位置偏差、
   对宿主跟随/回到底部的影响），批准后单独分支、默认关闭、CHANGELOG 显式声明
   「接管了一次滚动」。
4. (c)「接受整屏位移」在 P1 阶段**不允许**作为结论——它只能作为「R2 不成立」时的产品取舍，
   写回 Q1 的改判。

**不定会怎样**：B 模式在真机上「偶尔跳一下」，然后没人知道为什么。

## Q6 · 多 pane 时会不会出现 N 个 embedded 滚动容器？

**问题**：`[已证实]` 单 pane 多 tab 会有一个 embedded scroller；`preferNewPane` 的存在暗示
可能出现多个。目前只复现了单个。

**我的建议**：不影响设计（我们一律排除 `[data-sidebar-chat]`），但 `HostAdapter.current()`
必须在这种情况下**返回 null 并冻结**，而不是猜一个。需要一次实测确认。

**不定会怎样**：极端布局下选错容器，重演 0.1.4 的事故。

## Q7 · `data-slot` / `data-conversation-*` 能否作为稳定契约？

**问题**：0.2 的所有容器识别都押在这组属性上。它们现在是宿主 renderer 的输出，但没有书面承诺。

**已定（2026-11-09）：不等宿主承诺**，自己做成可承受改版的适配层。三件事必须同时存在：

1. **版本感知**：启动时读宿主版本（`window.__DSH_*` / 版本字符串），与「已验证版本表」比对。
   表内命中 → 正常；表外 → 进「保守模式」（只做报纸、不做无缝/复制）。
2. **结构交叉校验**：容器识别不靠单一属性，而是**多信号投票**
   （`data-slot="main"` + `data-conversation-region="chat"` + `data-content-phase` + 有内容行），
   至少 2 个信号一致才认。任一信号突然全页消失 → 视为宿主改版。
3. **失败冻结**：校验不通过时**不排版、不清残留、不猜**，保留上一次已知良好的布局，
   在徽标上显示「宿主结构已变化，已冻结」。宁可不动，不可乱动。

补充约束：三条策略的降级顺序是 **A 永远可用 → B/C 保守关闭**。报纸只依赖「可见行」，
是唯一可以在未知宿主结构下工作的模式。

**不定会怎样**：宿主一次改版，插件从「选错容器」变成「完全不工作」。

## Q8 · 0.2 的「线程」要不要记住每个会话的 mode / 列数？

**问题**：ThreadContext 已经按容器分片，但 0.2 只有活动线程。是否值得按会话持久化偏好？

**我的建议**：**列数按会话记，模式按全局记**。模式是「我现在想怎么读」，列数是「这个会话适合几列」。

**不定会怎样**：切换会话后列数被重置，用户每次都要重调。

---

## Q9 · 无缝模式要不要保留宿主的「跟随最新消息 / 回到底部」？

**问题**：R2 免费得到（`scrollTop ≡ 流位置`，宿主的 `nearBottom` 自动正确）；R3 必须自己实现。

**我的建议**：保留。它也是 R2 相对 R3 的关键优势之一。

**不定会怎样**：如果产品上不需要，R3 的成本会低很多——这是一个可能改变路线选择的输入。

---

## Q10 · 0.2 允不允许「模式切换导致内容重载」？

**问题**：三种模式共用同一个 `ContentModel`，理论上不重载。但复制模式可能需要不同的历史深度。

**我的建议**：不允许重载。同一会话的内容版本跨模式共享，历史深度只增不减。

**不定会怎样**：切一次模式重启一次加载，用户会以为卡了。
